# Roadmap do sandmux

Registro da exploração feita em 2026-11-12 e plano sequencial de desenvolvimento. Este arquivo é a memória do projeto: quando um change for proposto, os artefatos dele passam a valer sobre o que está escrito aqui, e este roadmap deve ser atualizado. As specs vigentes ficam em `openspec/specs/` desde o arquivamento do primeiro change, em 2026-11-13, e também valem sobre este roadmap.

Como ler: a seção 2 guarda todas as decisões já tomadas; a seção 4 organiza o trabalho em etapas, cada uma com os changes necessários, em ordem; a seção 7 liga cada pedido original ao change que o atende.

## 1. Visão

O sandmux é um multiplexador de terminal no estilo do tmux, escrito em Rust com ratatui, feito para subir harnesses de agente (opencode, hermes e outros) dentro de um sandbox de segurança.

O foco principal é o sandbox, não a interface:

- o agente fica confinado a uma pasta de trabalho;
- arquivos, pastas, rede, APIs de inferência e MCPs são controlados por allowlist e denylist;
- toda interação com arquivos e rede é registrada;
- nenhum segredo real existe dentro do sandbox: chaves são trocadas no tráfego de saída e credenciais de banco são injetadas por um MCP próprio.

**Princípio condutor**: seguro por padrão, com o mínimo de atrito. Uma baseline segura vem embutida e funciona sem configurar nada; o usuário só gerencia exceções. Na dúvida, prefere-se o padrão que não quebra programas.

## 2. Decisões tomadas

### 2.1 Plataforma e binários

| Tema | Decisão |
|---|---|
| Sistema | Apenas Linux |
| Isolamento | seccomp e Landlock, mais namespaces (user, mount, network, pid) |
| Binários | Quatro, separados: cliente `sandmux` (linha de comando e TUI), daemon de sessões `sandmuxd`, lançador do sandbox `sandmux-run`, auxiliar root `sandmux-helper`. Substitui o pedido original de binário único |
| Persistência | Os agentes sobrevivem ao fechar o terminal, como no tmux |
| Instalação | Pede `sudo` logo de início. Se recusado ou indisponível, instala no modo sem privilégio |
| Sem suporte de kernel | Sem Landlock e user namespace, o agente não sobe. Nunca existe aba sem sandbox |
| eBPF | Fica no roadmap, como otimização. Liga sozinho quando distro e kernel suportam; sem suporte, vale a pilha sem privilégio |
| Regras do eBPF | O eBPF pode ter regras exclusivas. Cada uma é marcada como obrigatória (a aba não sobe sem eBPF) ou opcional (sobe com aviso) |
| Ameaça alvo | Agente manipulado por prompt injection, tentando ativamente ler segredos e exfiltrar dados. Exploit de kernel fora do escopo |
| Nome | `sandmux`, escolhido pelo usuário em 2026-11-12. Substitui `asmux`, escolhido antes no mesmo dia, e o nome de trabalho `agentmux`. Os binários seguem o nome: `sandmux`, `sandmuxd`, `sandmux-run`, `sandmux-helper` |
| Licença | MIT. Era MIT e Apache-2.0 em licença dupla; trocado para MIT apenas por decisão do usuário (2026-11-17) |
| Distribuição na v1 | Binário estático com script de instalação, `cargo install`, pacotes deb e rpm, AUR e Homebrew |
| Distros suportadas na v1 | Ubuntu LTS atual (26.04), Debian estável (13), Fedora atual e Arch: são as testadas e prometidas. O Ubuntu 24.04 com o kernel original (6.8) fica de fora pelo requisito de kernel do primeiro change; o change 74 (etapa 15) o traz de volta, pelo kernel HWE ou pelo auxiliar root com o BPF LSM ligado no boot |

### 2.2 Política e configuração

| Tema | Decisão |
|---|---|
| Camadas de política | Baseline embutida, preset do harness, `[global]`, perfil nomeado, perfil do projeto e opções do `run` (aba, quando a TUI chegar). Nas opções de liga e desliga vence a camada mais específica; as listas se somam, e um caminho em `ro` e `rw` de camadas diferentes é decidido pela mais específica (decisão do usuário, 2026-11-13, change 3). "Negar sempre vence" passa a valer para as listas de negação das etapas de rede e arquivos |
| Arquivo de configuração | TOML, em `$XDG_CONFIG_HOME/sandmux/config.toml` (por padrão `~/.config/sandmux/config.toml`), com seções `[global]`, `[profile.<nome>]` e `[project."<pasta>"]`. Guarda só a diferença em relação às camadas embutidas. Arquivo inválido recusa o lançamento, com a linha. Editado por `sandmux config set/unset/add/remove/show/list` ou à mão, com comentários preservados (decisão do usuário, 2026-11-13) |
| Gerenciamento | Cada regra aparece como "padrão" ou "modificada", com a camada de origem (`sandmux config show`); desligar regra da baseline é ato explícito. No change 3 os perfis só acrescentam ou ajustam `ro`, `rw`, `pass-env` (só nomes), `repo`, `kvm`, `gpu` e `clipboard`; desligar item da baseline fica para a etapa 6, com a tela de gerenciamento (decisão do usuário, 2026-11-13) |
| Perfil de um projeto | Lido só de fora da pasta de trabalho: fica na configuração do usuário, ligado ao caminho da pasta. Nada dentro da pasta altera a política, porque o agente poderia editar o arquivo. Custo aceito: o perfil não é versionado no repositório. Vale para a pasta e as subpastas; com projetos aninhados, só o da pasta mais próxima. Perfis nomeados são escolhidos com `sandmux run --profile <nome>` (decisão do usuário, 2026-11-13). A pasta de configuração do sandmux nunca pode ser gravada pelo sandbox |
| Toda aba tem sandbox | Não existe shell livre |
| Opções do `run` no primeiro change | `--workdir`, `--ro`, `--rw`, `--pass-env`, `--import`, `--no-import`, `--repo`, `--kvm`, `--no-gpu`, e `--` para repassar argumentos ao harness. Os nomes foram propostos na spec e ainda não foram revisados pelo usuário |
| Diretório de dados | `$XDG_DATA_HOME/sandmux` (por padrão `~/.local/share/sandmux`), com os HOMEs sintéticos, as camadas de escrita, a pasta de entrada e os manifestos de importação |
| Listas embutidas | O conteúdo inicial de cada lista (arquivos sensíveis de `/etc`, credenciais por toolchain, padrões de arquivo de segredo, catálogo de exfiltração, catálogo de domínios comuns) é proposto na spec do change que a usa, para revisão item a item. As do primeiro change estão na spec `sandbox-filesystem` (arquivos de `/etc`, toolchains e seus arquivos de credencial, caches, credenciais conhecidas para o aviso de montagem) e na `harness-state-import` (o que é copiado de cada harness) |
| Atualização dos catálogos | Só com versão nova do sandmux: os catálogos são versionados junto com o binário, e o sandmux nunca faz chamada de rede por conta própria |

### 2.3 Arquivos

| Tema | Decisão |
|---|---|
| Visão do agente | Pasta de trabalho, HOME sintético, sistema em somente leitura e toolchains lidas do host |
| Pasta de trabalho | Por padrão, a pasta de onde o `run` foi executado. É a pasta real do host, montada no mesmo caminho com leitura e escrita, e não uma cópia: o que o agente cria aparece no host na hora, e o que já está nela (um PDF, por exemplo) aparece para o agente. O HOME é separado; a pasta de trabalho, não. Confirmado pelo usuário em 2026-11-12 |
| `/etc` | Substituir em vez de negar: `passwd` e `group` gerados, arquivos sensíveis cobertos |
| HOME sintético | Um por harness, compartilhado entre abas |
| Toolchains do HOME real | Só lista conhecida (nvm, bun, cargo, rustup, uv, pyenv, go, linuxbrew), sem arquivos de credencial. O host nunca é alterado |
| Instalações globais | As toolchains são lidas do host e escritas numa camada privada por harness, o mesmo mecanismo dos caches. `cargo install`, `npm install -g`, `rustup component add` e `go install` funcionam dentro do sandbox. Substitui a decisão anterior de toolchains em somente leitura |
| Caches de pacotes | Lidos do host, escritos numa camada privada. Uma camada por harness, compartilhada entre abas e pastas de trabalho. A spec propõe também os caches de navegadores do Playwright e de modelos do Hugging Face, com os tokens do Hugging Face cobertos; os dois não estavam na lista original e aguardam revisão |
| Arquivos com cara de segredo na pasta de trabalho | Escondidos do agente (não abrem; o nome ainda aparece no `ls`, decisão do change 15). Lista padrão aprovada pelo usuário em 2026-11-14 (change 16). O agente pode criar arquivos assim e continua vendo os que ele mesmo criou. Chega junto com a interceptação de arquivos, na etapa 6. Esconder antes, já no primeiro change, os arquivos que existem na hora do lançamento foi considerado e descartado pelo usuário em 2026-11-12 |
| Denylist de arquivo | Efeito imediato no agente em execução |
| Interceptação de arquivos | Seccomp user notify (decisão do usuário, 2026-11-14, depois de medir: 1,0x a 1,3x no uso normal contra 2x a 7x do FUSE). O supervisor abre toda abertura no lugar do processo e decide pelo arquivo aberto (sem a corrida da troca do caminho), conferindo as regras do Landlock, que segue valendo para o resto. O registro cobre só as pastas do agente. Com o auxiliar root, o BPF LSM e o escopo próprio da aba, o kernel decide e registra (change 78, decisão do usuário de 2026-11-20): marcas por inode nos segredos (`ENOENT`) e no `file-deny` (`EACCES`), aberturas pela fila do kernel; o supervisor fica como recuo |
| Liberar pasta nova | Vale na hora, sem reiniciar o agente. Aparece em `/mnt/sandmux/<nome>`, liberada para escrita desde o início (decisão do usuário, 2026-11-14, change 26) |
| User namespaces aninhados | Permitidos. Navegadores headless que se isolam funcionam; ferramentas que precisam montar (podman sem root, bubblewrap) não, porque um processo sob Landlock não monta nada |
| `.git` da pasta de trabalho | `.git/hooks` e `.git/config` em somente leitura. O agente faz commit, branch e merge; não cria hook, não adiciona remote e não grava o upstream de uma branch. Impede que algo plantado pelo agente rode fora do sandbox quando o usuário usa o git no host. A brecha do `.git/commondir` criado pelo agente fica para a etapa 6 (decisão de 2026-11-13). O `.git/commondir` criado pelo agente passou a ser negado no change 16 (abertura, rename, link e symlink) |
| Pasta de trabalho perigosa | Quando é o HOME, a raiz ou uma pasta que contém o HOME, o `run` recusa sempre e explica. Não existe opção de forçar: o usuário voltou atrás dela em 2026-11-12, por ser mais simples. Na implementação foram acrescentados o diretório de dados do sandmux e qualquer pasta que o contém (como `~/.local`), que dariam ao agente acesso às camadas e aos HOMEs sintéticos dos outros harnesses |
| Pasta de trabalho que é um worktree do git | O sandmux detecta e monta o diretório git do repositório principal, com hooks e config em somente leitura. O agente alcança o histórico e as branches dos outros worktrees |
| Pasta de trabalho que é subpasta de um repositório | Por padrão sobe sem git, com aviso. Uma opção explícita monta o repositório inteiro em somente leitura, com a subpasta gravável e o `.git` protegido |
| Dispositivos | A GPU entra em todo sandbox por padrão, quando existe na máquina. `/dev/kvm` só por opção explícita. O resto do `/dev` continua mínimo |
| Identidade do git | O HOME sintético recebe um gitconfig mínimo, gerado só com `user.name` e `user.email` copiados do gitconfig real. Aliases, credential helpers e URLs com token ficam de fora |
| Pasta de entrada | Uma pasta do sandmux no host, visível em somente leitura em todo sandbox, num caminho fixo (`~/inbox`, informado pela variável `SANDMUX_INBOX`). É o caminho para entregar ao agente um arquivo de fora da pasta de trabalho (screenshot, PDF). Na TUI, colar uma imagem grava nela e escreve o caminho no terminal |

### 2.4 Rede

| Tema | Decisão |
|---|---|
| Modos por aba | Quatro: **aberta** (padrão), **só inferência**, **sem rede**, **custom** |
| Modo aberta | Tudo liberado e registrado; bloqueio pela denylist, com efeito imediato |
| Denylist do modo aberta | Já vem com catálogo de destinos de exfiltração conhecidos, habilitado; itens podem ser desligados |
| Modo custom | Bloqueado por padrão. Allowlist com itens habilitados ou desabilitados. Catálogo de domínios comuns (domínios individuais, com curingas) que vem desabilitado. Domínios próprios podem ser cadastrados, habilitados ou não |
| Liberar no modo custom | Um domínio bloqueado pode ser liberado direto da lista de bloqueios do painel, do mesmo jeito que um acesso novo vai para a denylist. A liberação entra na allowlist da aba ou do perfil e vale na hora |
| Rede local | No modo aberta, inclui a rede local e os serviços da máquina. Metadados de cloud sempre bloqueados |
| Serviços da máquina | Alcançados por um nome especial, informado ao agente |
| Portas abertas pelo agente | Publicadas automaticamente no `localhost` do host e listadas no painel |
| Decifração de TLS | Só nos domínios com segredo a injetar; ampliável por perfil |
| Log de rede | Domínio, método e caminho, sem corpo. Onde não há decifração, domínio e volume |
| Retenção do log | 30 dias com teto de tamanho, ajustáveis |
| QUIC (HTTP/3) | Bloqueado. Os programas caem para TLS comum, onde o domínio aparece e a troca de chave funciona |
| Outros protocolos TCP e UDP | No modo aberta, passam e são registrados por domínio, IP e porta. Nos modos custom e só inferência, só passa o que casa com a allowlist |
| Conexão direta por IP, sem consulta de DNS | No modo aberta, passa, registrada e destacada como "sem domínio" |
| Ping | Não funciona dentro do sandbox |
| Aviso de domínio novo ou de bloqueio | Destaque no painel lateral e marca na aba, visível de outra aba. Nada fora do sandmux |
| Interface de rede | Criada por sandbox, sem privilégio; não precisa de interface criada na instalação |
| Política de rede (change 9) | Modos `aberta`, `inferencia`, `custom` e `sem-rede`; denylist (`deny`, `--deny`) em todo modo, com o catálogo de exfiltração ligado; allowlist do custom (`allow`, `--allow`, `allow-off`, grupos do catálogo comum em `catalog`); catálogo de provedores no modo só inferência; `catalog-off` desliga itens dos catálogos. Padrões: domínio exato, `*.domínio`, IPv4 e CIDR. Negar sempre vence. Nos modos restritos, o IP precisa ter vindo de uma consulta a um nome liberado |
| Efeito imediato (change 9) | O daemon grava a política de cada lançamento num arquivo em `$XDG_RUNTIME_DIR/sandmux/net/`, recompila quando o arquivo de configuração ou a camada da aba mudam, e o gateway relê o arquivo a cada decisão. O `run` sem terminal fica com a política do lançamento. Entrar ou sair de `sem-rede` vale no próximo lançamento |
| Onde roda o gateway | No supervisor do `sandmux-run`, fora do sandbox, e não no daemon: vale também no `run` sem terminal, e vive exatamente enquanto o sandbox vive. O TUN é criado pelo processo 1 no namespace novo e passado ao supervisor por SCM_RIGHTS; a pilha TCP/IP é o `ipstack` sobre tokio, no crate `sandmux-net` (change 8) |
| Endereços | Sandbox `10.0.2.100/24`, rota padrão `10.0.2.2`, DNS `10.0.2.3`, máquina `10.0.2.254` com o nome `host.sandmux.internal` (levado ao `127.0.0.1` do host) e a variável `SANDMUX_HOST`. Só IPv4 (change 8) |
| Registro de rede | Linhas JSON por dia em `$XDG_STATE_HOME/sandmux/net/`, com etiqueta `s<sessão>-<n>` ou `run-<pid>`, e `new` pelo primeiro acesso ao domínio na pasta de trabalho. Retenção pelo daemon com `net-log-days` e `net-log-max` em `[global]`. Consulta por `sandmux net [<id>]` e pelo pedido `Net` do protocolo 7 (change 8) |

### 2.5 Segredos

| Tema | Decisão |
|---|---|
| Regra | Nenhum segredo real dentro do sandbox |
| Cofre | Arquivo cifrado com senha, digitada quando o daemon sobe. Opcionalmente, a senha fica no keyring do sistema e o daemon abre o cofre sozinho (change 47, decisão do usuário de 2026-11-15: só a senha, ligado por comando) |
| Após reboot | O daemon volta sozinho no login do usuário; os agentes esperam a senha do cofre |
| Troca de chave | Chave falsa no sandbox, trocada pela real no tráfego, só quando o destino é o dono da chave |
| Provedor da v1 | OpenRouter, com API key |
| OAuth | Desejado; fica no roadmap |
| Git | ssh-agent controlado: chaves escolhidas por perfil, uso livre com registro, SSH de saída restrito aos servidores git cadastrados. As chaves ficam no cofre, e o daemon assina sem o ssh-agent do host (decisão do usuário, 2026-11-14, change 14) |
| Tokens de ferramentas de desenvolvimento | Segredo genérico por domínio, na v1: o cofre aceita qualquer token ligado a um domínio (GitHub para o `gh`, registries privados de npm, pip e cargo). O agente usa um valor falso e a troca acontece no tráfego, como na inferência. Implementado no change 25: cada segredo tem ferramentas (`gh`, `git`, `npm`, `pip`, `cargo`, `docker`), o falso chega pela configuração só daquela execução, e a troca abre o `Authorization: Basic` |
| Até o cofre existir | `--pass-env`, desligado por padrão e com aviso, passa uma variável específica para dentro. No opencode, `OPENCODE_CONFIG_CONTENT` faz a variável vencer o `auth.json` importado. No hermes (decisão do usuário, 2026-11-13), o `~/.hermes/.env` daquela execução é um arquivo gerado, em somente leitura, com os valores reais no lugar dos falsos; o `.env` guardado continua falso. Valores com quebra de linha ou `${` são recusados |

### 2.6 Harnesses

| Tema | Decisão |
|---|---|
| v1 | opencode e hermes |
| Depois da v1 | Claude Code (preset `claude`, change 43) e oh-my-pi (preset `omp`, change 44), em 2026-11-15; Antigravity CLI do Google (preset `agy`, change 63), em 2026-11-15 |
| Hermes | Completo: gateway próprio, cron e canais de mensagem. Nunca usa o gateway do host |
| Canais do hermes na v1 | Telegram, Discord e Slack. WhatsApp fica para depois |
| Backend Docker do hermes | Não suportado dentro do sandbox |
| Importação | Config, skills, memórias do hermes e MCPs cadastrados. Sem sessões nem saídas de ferramenta. Segredos trocados por valores falsos, com o prefixo `sandmux-fake-`. A tabela de cada harness é uma lista de permissão: o que não está nela não é copiado. Pareamento de canais e tarefas agendadas do hermes ficam de fora de vez (decisão do usuário, 2026-11-14, change 20): são criados dentro do sandbox |
| Primeira execução de um harness | Com o HOME sintético vazio, o `run` pergunta uma vez se deve importar a configuração existente, mostra o que foi copiado e quais segredos foram trocados, e segue. Em uso não interativo, exige uma opção explícita |
| Reimportação | Rodar `sandmux import` de novo copia só o que ainda não existe no HOME sintético, nunca sobrescreve e mostra o que está diferente. Uma opção força sobrescrever |
| Preset `shell` | Um shell confinado, sem harness, lançado como qualquer harness (`sandmux run shell`), com HOME sintético próprio. Usa o shell do usuário (`$SHELL`) com um arquivo de configuração mínimo gerado pelo sandmux; o `.bashrc` e o `.zshrc` reais não são importados |
| Login do Antigravity CLI | Decisões do usuário (2026-11-16, change 66): o login do Google do `agy` sai do sandbox pelos dois caminhos, o login do host importado para o cofre e o login feito no sandmux capturado pelo gateway; o access real vai a todo `*.googleapis.com` (o refresh, só a `oauth2.googleapis.com`). Decisões do agente: a captura passa a ter um harness dono, e os segredos de login (`claude:*`, `agy:*`) só valem nas abas do harness dono |
| Harness não instalado | O `run` recusa e mostra como instalar o harness no host. O sandmux não instala harness |
| Atualização do harness | Feita fora do sandbox, pelo usuário, com o atualizador do próprio harness. Dentro, o código entra em somente leitura e o preset desliga a checagem de atualização: no opencode pela variável `OPENCODE_DISABLE_AUTOUPDATE`; no hermes pela chave `updates.check: false` do `config.yaml`; no Claude Code por `DISABLE_AUTOUPDATER`; no Antigravity CLI por `AGY_CLI_DISABLE_AUTO_UPDATE=true` (change 63) |
| MCPs importados | Liberados e registrados; o usuário desabilita os que não quiser |
| Controle de MCPs | Por servidor: cada servidor MCP é habilitado ou desabilitado inteiro. Sem controle por ferramenta |
| MCP de banco | PostgreSQL e MySQL. Leitura e escrita por padrão, com registro de cada query |

### 2.7 Interface

| Tema | Decisão |
|---|---|
| Layout | Abas, mais um painel lateral fixo para o registro de acessos. Sem painéis divididos genéricos |
| Atalhos | Tecla de prefixo, como no tmux, configurável. O padrão é Ctrl+b |
| Sessões | Um conjunto único de abas por usuário: todo cliente que se anexa vê as mesmas abas. No daemon, cada aba é uma sessão com o seu PTY. Sessões nomeadas, cada uma com as suas abas, ficaram para depois da v1 e vieram como grupos de abas no change 49 (cada TUI mostra um grupo) |
| Vários clientes | Vários terminais podem se anexar ao mesmo tempo e todos interagem. O tamanho da tela segue o menor terminal |
| Aba de harness encerrado | Continua aberta, com o código de saída e o histórico; uma tecla reinicia o harness na mesma pasta e outra fecha a aba |
| Histórico de tela | 10.000 linhas por aba, em memória, ajustável. Por padrão, some quando o daemon reinicia, e nada da saída do agente vai para o disco. Opcionalmente (`[global] screen-history`, change 54, decisão do usuário de 2026-11-15), a saída vai para o disco cifrada com uma chave do cofre, de forma contínua, e volta depois do reinício |
| Escrita no clipboard pelo harness (OSC 52) | Bloqueada por padrão; uma opção por perfil ou aba libera. Selecionar e copiar pela TUI do sandmux funciona sempre |
| Início do daemon | No login do usuário. Subir no boot, sem login, fica para depois da v1, junto com o keyring |
| Daemon antes da TUI (change 2, decisões do usuário em 2026-11-13) | Com terminal, `sandmux run` cria uma sessão no daemon e anexa; sem terminal (script, pipe, CI), roda direto, sem daemon, como no change 1. Anexar sem TUI: o terminal do usuário vira o da sessão, o histórico é reenviado e a tela redesenhada; Ctrl+b d desanexa e Ctrl+b Ctrl+b envia Ctrl+b. A escrita no clipboard é liberada por sessão com `sandmux run --allow-clipboard`; a consulta do clipboard é sempre bloqueada |
| Como o daemon sobe | Unidade systemd de usuário, instalada e habilitada pelo próprio cliente na primeira vez em que ele precisa do daemon, com aviso; sem systemd, o cliente sobe o daemon na hora. `sandmux daemon disable` remove a unidade |
| Restauração após reboot | O daemon relança sozinho as sessões que estavam vivas, na mesma pasta e com as mesmas opções. As que usavam `--pass-env` ficam paradas até o usuário reiniciá-las de um terminal com as variáveis, porque os valores nunca vão para o disco |
| Versões diferentes de cliente e daemon | O cliente recusa, mostra as duas versões e indica `sandmux daemon restart`, que relança as sessões como após um reboot. Nada reinicia sem o usuário pedir |
| Programas com janela | Não abrem na v1: Wayland e X11 ficam fora do sandbox. Navegador headless funciona |
| Recursos | Teto generoso de processos e memória por aba, ajustável. Decisões do usuário em 2026-11-13 (change 4): só memória e processos, sem CPU; padrões de 75% da RAM (sem swap no sandbox) e 8192 processos e threads; o `run` sem terminal recebe os mesmos tetos; o consumo aparece em colunas do `sandmux ls` e o detalhe em `sandmux stats`. Os tetos vêm de um escopo transitório do systemd de usuário por lançamento; sem suporte, a sessão roda sem teto, com aviso |
| Pedidos originais | Atalhos para navegar entre abas, modal com lista de abas, clique do mouse, nome de aba customizável, temas para abas, componentes, janelas e botões |

### 2.8 Ferramentas de desenvolvimento

Pedido de 2026-11-12: os usuários serão desenvolvedores e precisam do que desenvolvedores usam no dia a dia, como o Docker, sem abrir mão do confinamento.

| Tema | Decisão |
|---|---|
| Socket do Docker do host | Nunca entra no sandbox. Ele equivale a root na máquina |
| Docker para o agente | Um Docker sem root, privado do sandbox, iniciado pelo sandmux fora do Landlock. O agente recebe só o socket dele. `docker` e `docker compose` funcionam; montagens só alcançam o que o sandbox já enxerga; `--privileged` não dá privilégio real |
| Rede dos contêineres | Passa por um gateway do sandmux no daemon, com o mesmo DNS, os mesmos bloqueios e o mesmo registro do sandbox (etiqueta `docker-<id>`), e a política mais restrita entre as sessões vivas da pasta (change 10). De dentro do sandbox, as portas publicadas são alcançadas por `host.sandmux.internal` (change 8) |
| Imagens e contêineres | Separados dos do host. O agente não vê nem altera os contêineres que o usuário roda fora |
| Divisão do Docker privado | Um por pasta de trabalho. Imagens e volumes persistem entre sessões do mesmo projeto; os contêineres só enxergam aquele projeto e seguem a política de rede da aba. Um cache local de downloads evita baixar a mesma imagem de novo em outro projeto |
| Duas abas na mesma pasta | Dividem o mesmo Docker privado. Com modos de rede diferentes, vale para os contêineres o mais restrito |
| Máquina sem Docker rootless | O agente sobe sem Docker; `docker` lá dentro falha com mensagem clara e o diagnóstico diz o que instalar. Na v1 o único motor suportado é o Docker rootless |
| CLIs de cloud (`aws`, `gcloud`, `kubectl`, `terraform`) | Na v1, liberação explícita: o usuário monta a credencial de propósito (`--ro ~/.kube`), com aviso de que ela fica ao alcance do agente. Depois da v1, credencial temporária gerada fora do sandbox |
| Quando | Etapa 2, com o daemon, que mantém o Docker privado vivo junto com a sessão |
| Instalações globais | Camada privada de escrita sobre as toolchains (seção 2.3) |
| `gh` e registries privados | Segredo genérico por domínio (seção 2.5) |

## 3. Arquitetura

### 3.1 Binários

```
+----------------+  socket  +----------------------+  socket  +----------------+
| sandmux        |<-------->| sandmuxd             |<-------->| sandmux-helper |
| cliente        |          | daemon de sessoes    |          | auxiliar root  |
| (CLI e TUI)    |          | PTYs, cofre,         |          | eBPF           |
+----------------+          | registro, politica   |          | (roadmap)      |
                            +----------+-----------+          +----------------+
                                       |
                                       | especificacao de lancamento
                                       v
                            +----------------------+
                            | sandmux-run          |
                            | lancador do sandbox  |
                            | gateway de rede      |
                            +----------+-----------+
                                       |
                                       v
                                    harness
```

Fronteiras de confiança: o cliente não toca em segredo nem em sandbox; o daemon não tem código de interface; o lançador só aplica uma especificação pronta; o auxiliar root não tem rede, TLS nem banco.

### 3.2 Camadas do sandbox

```
  agente (opencode, hermes)
     |
     |  chamadas de sistema            trafego de rede
     v                                    v
+----------------------------+   +---------------------------+
| seccomp: nega chamadas     |   | network namespace:        |
| perigosas; interceptacao   |   | sem rota de saida, tudo   |
| de aberturas de arquivo    |   | passa pelo daemon         |
+----------------------------+   +-------------+-------------+
| Landlock: o que pode ser   |                 |
| feito com o que existe     |                 v
+----------------------------+   +---------------------------+
| mount namespace: o que     |   | gateway: politica de      |
| existe para o agente       |   | dominio, decifracao, troca|
+----------------------------+   | de chave, registro        |
| user e pid namespaces      |   +-------------+-------------+
+----------------------------+                 |
                                               v
                                  internet e rede local
```

### 3.3 Níveis de proteção

```
a cada inicio do daemon: detecta o suporte da maquina
      |
      +-- tem eBPF --------> nivel 2: observacao e regras no kernel   (roadmap)
      +-- nao tem ---------> nivel 1: seccomp + Landlock + namespaces (v1)
      +-- nem isso --------> recusa subir o agente
```

O nível ativo é sempre visível na interface e no diagnóstico.

## 4. Etapas e changes

Cada etapa é desenvolvida em sequência. Dentro de uma etapa, cada change passa por proposta, validação, implementação e arquivamento antes do seguinte. Nomes de change são provisórios até a proposta. O número é só um identificador: a ordem de desenvolvimento é a das tabelas.

Situação: **feito**, **em planejamento** (artefatos parciais) ou **a propor**.

A ordem das etapas foi confirmada: daemon e TUI vêm antes de rede e cofre. O cofre precisa do daemon para pedir a senha, o bloqueio imediato precisa de um processo de longa duração, e cada etapa a partir da 3 entrega junto a sua tela de gerenciamento.

### Outras lacunas do backend eBPF

Levantadas pelo agente em 2026-11-17, a pedido do usuário, pela leitura das specs e pelo que o agente conhece do kernel. Nada foi testado, e nenhuma tem change. Ficam além do confinamento do Docker privado (change 70) e das coberturas que caem para um contêiner privilegiado (seção 6).

| Lacuna de hoje | O que o eBPF daria | Ressalva |
|---|---|---|
| Não há registro do que o agente executa. O registro de arquivos cobre `open`, `openat`, `openat2` e `creat`, e só nas pastas do agente; um `curl` de `/usr/bin` não deixa linha | Um registro de execuções, com o binário e os argumentos, pelo gancho de execução do kernel | Só observa. Seria uma regra opcional |
| O registro de rede não diz qual processo abriu a conexão | O processo de cada conexão, para separar a chamada de inferência do harness de um `curl` lançado por uma ferramenta | Entregar a chave real só ao binário do harness também ficaria possível, mas só sobe a barra: o agente pode depurar o harness dentro do sandbox |
| Ferramentas que montam (bubblewrap, podman sem root) não rodam no sandbox, porque um processo sob Landlock não monta nada | A política de arquivos decidida pelo arquivo, e não pelo caminho, que deixa de depender de proibir montagens | A mais cara: exige marcar árvores de pastas no kernel |
| O Ubuntu 24.04 com o kernel 6.8 fica de fora, por faltar o escopo de sockets abstratos e de sinais do Landlock | Os dois escopos em BPF LSM. Seria uma regra obrigatória: nessa máquina a aba só subiria com eBPF | Visto em 2026-11-20: o `bpf` não está entre os LSMs padrão do 24.04, e o usuário precisa ligá-lo no boot. É o change 74 |
| A interceptação de arquivos do próprio agente custa de 3,1x a 3,5x em leitura em massa e depende de emulação (tradução do `/proc/self`, namespaces aninhados, `lsof` limitado) | A decisão e o registro dentro do kernel, sem ida e volta ao supervisor | É a otimização, o motivo original deste item, que o usuário deixou em segundo plano em 2026-11-16 |

Sugestão do agente, aceita pelo usuário em 2026-11-17 (etapa 15, changes 72 e 73): depois do change 70, o registro de execuções e o processo de cada conexão. Os dois usam a mesma base do change 70 (programas presos ao cgroup e uma fila de eventos) e só observam.

O que parece caso de eBPF e não é:

- **Regra de rede nova não corta as conexões abertas, e conexão longa só aparece no registro quando termina:** o gateway termina as duas pontas e pode resolver os dois sozinho.
- **SNI vazio atrás de uma CDN:** sem o nome, nenhum mecanismo sabe o domínio.
- **Aberturas com `O_PATH` fora do registro, e o nome do segredo aparecendo no `ls`:** pelo que o agente conhece, o kernel não tem gancho para nenhum dos dois.
- **Superfície do kernel exposta** (drivers de GPU, Docker): o eBPF não corrige falha de kernel.
- **Tetos de memória e de processos numa máquina sem systemd de usuário:** dependem do auxiliar root (`sandmux-helper`), e não do eBPF.

### Riscos conhecidos e aceitos

- **Change 78, arquivos das abas pelo kernel (2026-11-20):** um segredo criado no host durante a sessão fica legível por até ~1 s, até a vigia marcá-lo (aceito pelo usuário). Com o auxiliar morto à força (`SIGKILL`, um travamento), sobra uma janela curta entre a saída dele e o congelamento da aba; a saída limpa não tem janela. Se o daemon morre com a aba congelada, ela fica congelada. Uma leitura em massa pode encher a fila de 1 MiB: as aberturas a mais saem do registro, contadas na linha de descarte, e nada é negado por isso. O shell de entrada (`Ctrl+b t`) continua com o supervisor, e uma abertura de leitura e escrita aparece como `w`.
- **Fechado em parte pelo change 79 (2026-11-20), só no 6.8 (Landlock ABI 4):** o lançamento recusado logo depois de um reinício do auxiliar tinha duas causas, as duas tratadas no change 79. A primeira: o auxiliar antigo aceitava conexões novas na saída limpa e as cortava. A segunda: carregar e soltar os programas globais do escopo leva segundos no 6.8 (o `ftrace` espera o RCU Tasks a cada um), e a troca de auxiliar somava as duas coisas. **Ainda aberto:** em 1 de 7 rodadas completas dos testes com root na VM, depois do change 79, um lançamento ficou 30 s sem registrar o escopo (o auxiliar antigo demorou a sair) e foi recusado. Nada rodou sem o escopo. Não se repetiu em 6 rodadas seguidas com uma vigia das pilhas do auxiliar ligada.

- Um contêiner do Docker privado roda no user namespace do `rootlesskit`, sem o Landlock e sem o supervisor de aberturas do sandmux. A visão de arquivos é a mesma do sandbox, o que protege credenciais e o resto do HOME. O user namespace sem privilégio impede módulos e montagens no host. Registrado pelo agente no change 24 (2026-11-13), sob a autorização do usuário de seguir sem parar; pode ser revisto. Desde o change 69 (2026-11-17), todo processo do Docker herda um filtro seccomp do sandmux com as chamadas que o sandbox nega, menos as de montagem, também com `--privileged` e `seccomp=unconfined` (teste `conteiner_privilegiado_herda_o_filtro`).
- **Achado em 2026-11-16, na exploração do backend eBPF; reduzido pelo change 69 (2026-11-17), não fechado:** os segredos e o `file-deny` que existem quando o Docker sobe chegam vazios aos contêineres comuns (teste `conteiner_nao_le_os_segredos_da_pasta`). Continuam abertos: os arquivos criados depois, a política ao vivo, o `.git/commondir`, o registro de arquivos e o contêiner privilegiado (item abaixo), que ficam para o change 70. O texto original: as regras de arquivo que só o supervisor de aberturas aplica não valem para o Docker privado. O `exec_view` do lançador sobe o `dockerd` sem Landlock, sem seccomp e sem o supervisor, e a visão do Docker monta a pasta de trabalho com um bind comum, só com a proteção do `.git`. Pela leitura do código, um contêiner com a pasta de trabalho montada (`docker run -v $PWD:/w ...`) abre os arquivos com cara de segredo que o agente não abre (`.env`, `*.pem`), ignora `file-deny` e `file-allow`, pode criar `.git/commondir` (a brecha fechada no change 16) e não deixa linha no registro de arquivos. A rede não tem essa lacuna: o Docker já passa pelo gateway (change 10). A spec `file-policy`, os testes de `docker.rs` e os limites de `docs/docker.md` não tratam do caso. Falta confirmar com um teste: um `.env` criado no host e lido por um contêiner. A correção em estudo é o backend eBPF (seção 5): BPF LSM filtrado pelo cgroup `sandmux-docker-<id>.slice`, carregado pelo `sandmux-helper`; as decisões pendentes estão em "Decisões ainda não tomadas".
- **Achado em 2026-11-16, na mesma exploração; fechado pelo change 69 (2026-11-17):** a visão do Docker passou a ter o `/dev` mínimo do sandbox, e um contêiner com `-v /dev:/d` não vê os pseudoterminais do host (teste `conteiner_ve_so_o_dev_minimo`). O texto original: a visão do Docker privado monta o `/dev` do host inteiro, com escrita e com as montagens de dentro dele (`compose_docker_view`), enquanto o sandbox do agente tem um `/dev` mínimo. Pela leitura do código e das permissões da máquina de referência, um contêiner com `-v /dev:/d` alcança o que o usuário alcança: os pseudoterminais dos outros terminais do usuário em `/dev/pts` (ler disputa as teclas digitadas, escrever põe texto na tela), a câmera (`/dev/video0`) e o áudio (`/dev/snd`), pela ACL do usuário e sem a opção `window`, e o `/dev/shm` do host. Corrigível sem eBPF, com um `/dev` mínimo na visão, como o do sandbox.
- **Achado em 2026-11-16, ao propor o change 69; fechado pelo change 69 (2026-11-17):** o Docker roda num cgroup namespace com raiz no escopo da pasta, e um contêiner com `-v /sys/fs/cgroup:/c` não vê o teto nem `user.slice` (teste `porta_so_no_localhost_teto_e_stats`). Na implementação apareceu um caso a mais: o escopo tinha o mesmo teto da slice e, como raiz do namespace, ficava ao alcance dos contêineres; o teto passou a ficar só na slice. O texto original: a visão do Docker privado monta o `/sys/fs/cgroup` do host com escrita, enquanto o sandbox do agente tem o `/sys` em somente leitura. Pela leitura do código, um contêiner com `-v /sys/fs/cgroup:/c` pode aumentar o teto de memória da própria slice ou matar outros cgroups do usuário, que são dele. Entra no change 69, com um cgroup namespace.
- **Achado em 2026-11-16, ao propor o change 69; a regra do kernel foi testada, o caminho pelo Docker não:** as proteções da visão do Docker feitas por montagem por cima (o somente-leitura de `.git/hooks` e `.git/config`, as coberturas de `/etc` e as coberturas novas do change 69) caem para um contêiner com `CAP_SYS_ADMIN` no user namespace do Docker (`--privileged`). Num teste em namespace próprio, um mount namespace do mesmo user namespace tirou o somente-leitura de um bind e desmontou a cobertura de um arquivo; num user namespace filho, as duas operações foram recusadas, porque as montagens ficam trancadas. O caso mais sério é o `.git`: um hook gravado assim roda no host quando o usuário usa o git. O sandbox do agente não tem esse caminho, porque nega as chamadas de montagem. Filtrar a API do Docker não resolve: o agente chega à raiz da visão por outros caminhos, como o socket do `containerd`. As saídas eram trancar a visão (montá-la num user namespace acima do que o `dockerd` usa) ou o eBPF. Decidido pelo usuário em 2026-11-17: só o eBPF, no change 70, que decide pelo inode; nas máquinas sem eBPF o limite fica aceito.

### Decisões ainda não tomadas

A última decisão antiga, o `--rw` sobre arquivos que o host executa (achado do change 3), foi decidida pelo usuário em 2026-11-15: recusar (change 40).

Decidido pelo usuário em 2026-11-16: o confinamento do Docker privado cobre os arquivos e as chamadas de sistema, e não só os arquivos; e o trabalho se divide em dois changes (69 e 70, etapa 14).
